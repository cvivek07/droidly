Restaurant Bill Screen in Kotlin

Build a restaurant bill screen on Android: Repository, StateFlow, ViewModel and RecyclerView. A common Android machine coding round question.

By Vivek Choudhary, Android engineer · Updated October 2026

HardAbout 60 minBuild it in Android Studio

Problem

Design and implement the restaurant bill screen below. Fetch bill data from a dummy API (simulated with a 1.5s delay), show a loading state, then render the check. This is a UI-focused machine coding challenge.

Target Screen
Toast
Burger$8.99
Fries$3.49
Soda$1.99
Ice Cream$1.99
Total:$15.67
Print
Pay $15.67
Header
  • Background: #FFFFFF · Padding: 12dp
  • "Toast" text — color #404040, size 16sp
Item List (RecyclerView)
  • Each row: item name (left) + price (right)
  • Scrollable — list length is dynamic from API
  • Show loading spinner while fetching
Footer
  • Background: #FFFFFF · Padding: 12dp
  • Total text — color #404040, size 16sp
  • Two buttons side by side · Height: 48dp
  • Margin top (from total): 8dp · Between buttons: 8dp
  • Button bg: #022CFA · Text: #FFFFFF, size 16sp
Dummy API — Mock this in your Repository
{
  "items": [
    { "name": "Burger",    "price": 8.99 },
    { "name": "Fries",     "price": 3.49 },
    { "name": "Soda",      "price": 1.99 },
    { "name": "Ice Cream", "price": 1.99 }

  "total": 15.67

// Simulate network latency: delay(1500) before emitting data

Requirements

  • Architecture: MVVM — ViewModel + Repository + sealed UiState
  • Use StateFlow in ViewModel, collect with repeatOnLifecycle(STARTED)
  • Use StateFlow.update { } — not .value =
  • Repository returns Flow<CheckData> with delay(1500)
  • Handle Loading → Success → Error states in the UI
  • Total amount and Pay button text must come from API data — do not hardcode

Hints

Hint 1

Start with data models: data class CheckItem(val name: String, val price: Double) and CheckData(items, total). Then define a sealed CheckUiState with Loading, Success(data), Error(message).

Hint 2

Repository: fun getCheck(): Flow<CheckData> = flow { delay(1500); emit(mockData) }. ViewModel: private val _state = MutableStateFlow<CheckUiState>(Loading) — call .update{} never .value =.

Hint 3

In the Activity: lifecycleScope.launch { repeatOnLifecycle(STARTED) { vm.state.collect { when(it) { ... } } } }. On Loading → show ProgressBar, hide RecyclerView. On Success → reverse + call adapter.submitList() + update footer text.

Hint 4

Footer layout: parent LinearLayout with weightSum="2", each button layout_weight="1". Pay button text = "Pay $" + String.format("%.2f", total) — read from state, not hardcoded.

Approach

Architecture Flow

Repository flow { delay(1500); emit(data) } → ViewModel collects + maps to CheckUiState via MutableStateFlow.update{} → Activity collects with repeatOnLifecycle(STARTED) → UI renders per state.

Key Files

  • CheckItem.kt / CheckData.kt — data models
  • CheckUiState.kt — sealed class with Loading, Success, Error
  • CheckRepository.kt — interface + impl with Flow + delay(1500)
  • CheckViewModel.kt — MutableStateFlow + viewModelScope + .update{}
  • BillActivity.kt — repeatOnLifecycle + adapter + footer update
  • activity_bill.xml — header / FrameLayout(RecyclerView + ProgressBar) / footer
  • item_check_row.xml — two TextViews, horizontal LinearLayout
What most candidates miss
  • Using .value = instead of .update { } — not atomic
  • Collecting Flow in onCreate scope — leaks coroutine when app is backgrounded
  • Hardcoding "Pay $15.67" — interviewer WILL change the mock data to test this
  • Not handling Error state — ProgressBar keeps spinning if the API call fails
  • ProgressBar outside FrameLayout — it won't overlay the RecyclerView properly
