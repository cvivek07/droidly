Sample Questions
The kind of questions you'll face
These are real questions asked in Android interviews at top product companies. Click any to see the kind of depth expected.
What is the difference between inline and noinline in Kotlin? When would you use each?
Medium ▼
Inline functions copy their body to call sites, eliminating lambda object allocation. noinline opts a specific lambda parameter out of inlining — needed when you want to store the lambda, pass it elsewhere, or return it. Good candidates use reified in the same breath, since reified type parameters only work in inline functions.
Explain Kotlin delegation — by keyword, lazy, observable. What problem does each solve?
Medium ▼
Class delegation via by forwards interface calls to a wrapped instance without inheritance. Property delegation separates "how a value is stored/computed" from the property itself. lazy defers init to first access (thread-safe by default). observable fires a callback on every write. Strong candidates mention ReadWriteProperty and how to write custom delegates — useful for Shared Preferences or Room-backed properties.
What is the difference between object, companion object, and a top-level function in Kotlin?
Easy ▼
object is a singleton — one instance, lazily initialised. companion object is tied to a class and its members are accessed via the class name (like Java static). Top-level functions have no enclosing class at all. The Java interop implications matter here: companion members need @JvmStatic to look like statics from Java; top-level functions compile to a class named after the file.
How does Kotlin's type system prevent null pointer exceptions? What are the edge cases where you can still get an NPE?
Hard ▼
The compiler tracks nullability at the type level and disallows unsafe dereferencing. Edge cases: Java interop (platform types have no nullability info), lateinit var accessed before initialisation, not-null assertion !!, and generics with nullable upper bounds. Strong candidates mention requireNotNull vs checkNotNull and how to use sealed types instead of nulls for domain modelling.
What is structured concurrency? How does coroutineScope differ from supervisorScope?
Hard ▼
Structured concurrency means a parent scope outlives all its children, and cancellation propagates both up and down. coroutineScope cancels all children if any one fails. supervisorScope isolates failures — one child failing doesn't cancel its siblings. You'd use supervisorScope when children are independent (e.g. loading multiple feed sections in parallel where one failing shouldn't kill the others).
What is the difference between StateFlow, SharedFlow, and Channel? When would you choose each?
Hard ▼
StateFlow holds a single value, always has a current state, and replays it to new collectors — great for UI state. SharedFlow is a hot stream with configurable replay and buffer — good for one-shot events. Channel is a rendezvous point — designed for producer/consumer with backpressure. Common mistake: using SharedFlow for navigation events without handling configuration changes properly.
How do you handle exceptions in coroutines? What happens if you throw inside launch vs async?
Medium ▼
In launch, uncaught exceptions propagate to the parent immediately and crash the scope unless a CoroutineExceptionHandler is installed. In async, the exception is held until .await() is called — so you must wrap await() in try/catch or the exception is swallowed. Strong answers mention that CoroutineExceptionHandler doesn't help in supervisorScope children by default.
Your ViewModel launches a coroutine that makes a network call. The user rotates the screen. What happens and what should you do?
Easy ▼
The ViewModel survives rotation, so viewModelScope coroutines continue running — the network call is not restarted. The new Activity/Fragment resubscribes to the StateFlow/LiveData and gets the current state. The job is only cancelled when onCleared() fires (user navigates away). This is one of the core reasons ViewModels exist.
What triggers recomposition and how do you prevent unnecessary recompositions?
Hard ▼
Recomposition is triggered when a State object read during composition changes. Compose skips recomposing a composable if all its inputs are equal (stability). To prevent unnecessary recompositions: mark data classes @Stable or @Immutable when safe, hoist state correctly, use remember to cache derived values, avoid reading unstable types inside composables, and use derivedStateOf when a computation depends on multiple states.
Explain the three phases of Compose rendering: composition, layout, drawing. Why does this matter for performance?
Medium ▼
Composition: builds the UI tree and observes state. Layout: measures and places nodes. Drawing: renders to canvas. Phases are incremental — Compose can skip earlier phases if only later ones are affected. For example, an animation that only changes a translation can skip composition and layout entirely (using Modifier.graphicsLayer) and run only the draw phase, keeping it on the render thread at 60fps.
What is the difference between LaunchedEffect, SideEffect, and DisposableEffect?
Medium ▼
LaunchedEffect runs a suspend block tied to a key — relaunches when the key changes, cancels when leaving composition. SideEffect runs after every successful recomposition — used to sync Compose state to non-Compose code (analytics, etc). DisposableEffect is for non-coroutine side effects that need cleanup (listeners, observers) — its onDispose runs when the composable leaves composition.
How does Clean Architecture apply to Android? Where exactly do you draw the boundaries?
Hard ▼
Three concentric layers: Data (repositories, data sources, DTOs), Domain (use cases, entities, repository interfaces), Presentation (ViewModel, UI state, composables). The dependency rule: inner layers never reference outer ones. Domain has zero Android imports. Use cases are plain Kotlin classes the ViewModel calls. Data layer implements domain interfaces. Common mistake: putting business logic in the ViewModel or referencing Android SDK classes in domain.
How do you handle one-shot UI events (navigation, snackbars) in MVVM without leaking them on rotation?
Hard ▼
The classic problem: StateFlow replays its last value, so a "navigate to Detail" event re-fires on rotation. Options: SharedFlow with replay=0 (events lost if no collector), Channel (buffered, consumed once), or the "consumed event wrapper" pattern (Event<T>). Google's current recommendation is SharedFlow combined with collecting only when the UI is in STARTED state using repeatOnLifecycle.
What is the Repository pattern? Why is it important even when you only have one data source?
Easy ▼
Repository abstracts data access behind a single interface, letting the ViewModel remain agnostic about whether data comes from network, cache, or DB. Even with one source today, the pattern pays off immediately in testing — you can inject a fake repository without touching Room or Retrofit. It also makes adding a cache layer trivial later: the ViewModel never changes, only the repository implementation does.
Design an image loading library for Android from scratch. What are the core components?
Hard ▼
Key components: Request queue (manages concurrent loads), Memory cache (LRU, bitmap pool to avoid GC pressure), Disk cache (bounded, LRU eviction), Decoder pipeline (BitmapFactory with inSampleSize for downsampling, hardware bitmaps for Compose), Network fetcher (OkHttp, HTTP cache headers), Lifecycle-aware request cancellation (cancels on Fragment/View detach), Placeholder/error state management. Strong answers address bitmap size estimation and why you must downsample before decoding.
Design a real-time chat feature for an Android app. How do you handle message ordering and offline delivery?
Hard ▼
Transport layer: WebSocket for real-time (long-lived), with SSE or HTTP polling as fallback. Local DB: Room stores all messages with a status column (sending / sent / delivered / read). Offline: write to Room first, enqueue with WorkManager (guaranteed delivery). Message ordering: server-assigned monotonic sequence ID, client uses local timestamp only for optimistic display. Conflicts resolved by server sequence on sync. Strong answers cover idempotency keys to prevent duplicate sends.
How would you build a robust Payment SDK as an internal platform service for an Android super-app?
Hard ▼
Core design: gateway-agnostic API contract (your SDK exposes PaymentProvider interface), pluggable adapters per gateway (Razorpay, Stripe, UPI), and a state machine for payment lifecycle (IDLE → INITIATING → PENDING → SUCCESS/FAILED/CANCELLED). Retry logic with idempotency keys so a network failure doesn't double-charge. Expose a result as a sealed class. Surface a PaymentResult callback and a webhook reconciliation path. Strong answers mention 3DS redirect handling and deep-link return flow.
